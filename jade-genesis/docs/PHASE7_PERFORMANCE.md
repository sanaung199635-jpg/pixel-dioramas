# Phase 7 性能报告

> **所有帧率目标均未实测。** 容器里没有 GPU，浏览器使用 SwiftShader（CPU 软件渲染的 WebGL 2），一帧要 150–800 ms。这个数字不能推断任何真实 GPU 上的帧率。下表记录的是**渲染工作量**：draw calls、三角形、GPU 对象数量。它们在任何设备上都相同，可以用来做前后对比。

## 目标（未实测）

| 平台 | 目标 | 状态 |
|---|---|---|
| 桌面 1920×1080 | 平均 ≥ 60 FPS，1% low ≥ 45 FPS | **未实测** |
| 移动（中端） | 平均 ≥ 30 FPS，无长时间严重掉帧 | **未实测** |

自适应画质（`app/Quality.ts`）未作改动：按帧时预算逐级调整像素比与阴影分辨率。

## 测量方法

- 工具：`tools/phase7-capture.cjs`。v1.0 与 Phase 7 的发布构建都放在 `/pixel-dioramas/jade-genesis/play/` 子路径下，用同一状态、同一镜头测量。
- `renderer.info` 统计一帧内的全部通道：阴影 + 透射 + 主通道（`autoReset = false`，每帧手动清零）。
- 渲染器：`ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero)), SwiftShader driver)`。
- 原始数据：`docs/phase7/before/stats-*.json`、`docs/phase7/after/stats-*.json`。

## 分析

- **第 01 幕（矿场）是主要成本：** draw calls +34%（86 → 115），三角形 ×2.4（197k → 480k）。
  - 第 02 幕在镜头远处仍会看到矿场，三角形也增加了 88%。
  - 第 01 幕各对象的三角形（单次绘制）：

    | 对象 | 三角形 |
    |---|---|
    | 极坐标地形 | 54k |
    | 原石 | 27k |
    | 侧面 | 11k |
    | 灌木 | 11k |
    | 碎石 | 10k |
    | 树冠 | 7k |

  - 地形、灌木、碎石和树冠会画三次：阴影、透射、主通道。
- **其他工位基本持平（±10%）：** 新增的门缝、螺栓、油缸等细节，由 `mergeByMaterial()` 合并抵消。
  - 第 02、03、06 幕的 draw calls 反而下降了 15–21%。
  - 第 08–09 幕的 draw calls 增加 8–24%：多出来的是机身细节在阴影通道里的绘制。
- **纹理：** 新增 6 张 128×128 的程序化 DataTexture：拉丝粗糙度 ×2、砂轮颜色和法线 ×2 组，另有一张摄影棚环境贴图（PMREM）。全部在启动时生成，**不需要下载任何文件**。
- **着色器程序：** 最多 49 个（v1.0 为 45）。多出的是地表材质和带纹理的金属、砂轮变体。
- **显存稳定性：** 12 幕循环三次，第二、三轮结束时几何体、纹理、程序数量相同。由回归测试“GPU memory stops growing…”验证，结果见 `PHASE7_VISUAL_REPORT.md` 的测试部分。
- **加载：** 发布构建的 JS 从 v1.0 的约 645 KB（gzip 约 177 KB）增加到 683 KB（gzip 191 KB），即 +38 KB（gzip +14 KB）。启动时额外的计算：生成地形网格与烘焙 AO（每个顶点采样 24 次高度）、生成纹理、生成 PMREM。在 SwiftShader 下加载到首帧的时间没有变长（桌面 10.3 s → 8.4 s；受机器负载影响，波动较大）。

## 如果真机帧率不达标，可以按顺序采取的措施

1. 低画质档关闭地形的投射阴影：阴影通道减少 54k 三角形。
2. 灌木改用单团树冠：三通道合计约减少 24k 三角形。
3. 地形网格从 192×139 降到约 176×119：三通道合计约减少 36k 三角形，台阶的圆滑度会略有下降。
4. 移动端降低透射通道的分辨率（three 0.170 没有现成开关，需要升级或自行实现）。

在拿到真机数据之前，这些措施都**没有启用**，以免无谓地牺牲画面。
